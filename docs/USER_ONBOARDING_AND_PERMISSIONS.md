# Research Atlas｜用户开通、使用与权限管理规范 V0.1

> **文档定位**：面向 Owner、管理员、科研成员和只读成员的统一操作规范，同时供开发者实施、测试和审计使用。  
> **版本**：V0.1 · 2026-11-14 · 状态：Draft（PR #65 开发分支）；**不是已在生产环境生效的用户协议**。  
> **适用系统**：Research Atlas 单团队工作台（Next.js + FastAPI + PostgreSQL），包括科研前台与同站 Development Studio。  
> **权限依据**：以服务端角色、会话和资源授权为准；页面隐藏按钮不等于权限控制。  
> **原则**：最小权限、邮箱本人验证、个人账户、邀请加入、关键动作审计、测试／生产隔离。

## 0. 请先区分三种“管理权限”

1. **Research Atlas 网站身份**：本文件定义的 Owner / Admin / Researcher / Viewer；决定谁能登录科研工作台、管理成员和操作研发台账。
2. **基础设施与源代码权限**：GitHub 仓库 Owner/Maintainer、Vercel 项目管理、Render 工作区/数据库管理员，是**不同的外部身份**。网站 Owner **不会**自动获得 GitHub 合并、生产部署、查看数据库密钥或操作 Render 的权限。
3. **科研内容审批权限**：研究题目、学术证据、论文评价、期刊来源变更等可以有独立业务审批人；**网站 Admin 角色不等于科研成果被认证**。Development Studio 的「审批同意」也不等于代码已经合并、生产配置已经发布。

当前数据库以**单一团队**为核心：研究画像、论文、想法、研究任务等属于团队共享数据，并没有完整的多组织租户隔离。任何“私人聊天”“团队共享聊天”的专属可见性规则应由对应对话模块**另行实现和验收**，不能从角色名称推断已经具备隔离能力。

## 1. 用户与身份类别

| 类别 | 获得身份的方式 | 典型使用者 | 核心职责 |
|---|---|---|---|
| **未登录／访客** | 无账户／未通过登录 | 未获邀请者 | 只能访问被明确设计为公开的内容；不能访问团队研究数据、研发管理接口 |
| **Owner（平台所有者）** | 首次由服务器预设邮箱发起，**本人通过邮箱链接认领** | 产品/实验室负责人 | 团队成员和管理员授权、平台级身份治理；可进入 Development Studio |
| **Admin（管理员）** | Owner 发出邀请，受邀邮箱验证并本人设置密码 | 受授权的项目技术或运营管理员 | 成员日常管理、研发台账和变更审批；**不得自行创建 Owner** |
| **Researcher（科研成员）** | Owner 或 Admin 邀请后邮箱验证 | 实验室成员 | 共享研究资源、发起科研任务、提交研究反馈；不能修改团队高级权限 |
| **Viewer（只读成员）** | Owner 或 Admin 邀请后邮箱验证 | 课题顾问、旁观者、审核查看者 | 查看获授权的团队信息；不能发起研究任务或修改共享画像 |

**角色是工作台权限，不是团队头衔。** “教授、博士、学生、合作导师、开发者”等组织称谓不直接映射角色；同一成员只能有一个当前平台角色。暂时不支持多团队、多组织或对同一用户按项目分别赋权。

### 1.1 角色决策边界

| 操作 | Owner | Admin | Researcher | Viewer | 代码/落地现状 |
|---|:---:|:---:|:---:|:---:|---|
| 使用有效账户登录研究工作台 | ✓ | ✓ | ✓ | ✓ | 已有会话、失效/撤销机制 |
| 阅读已授权的团队画像、论文、想法 | ✓ | ✓ | ✓ | ✓ | 已有团队认证接口；当前核心数据为团队共享 |
| 发起科研任务、提交 Idea 反馈 | ✓ | ✓ | ✓ | — | 服务端 `require_editor` |
| 修改正式团队共享研究画像 | ✓ | ✓ | — | — | 服务端 `require_admin`；画像版本冲突返回 409 |
| 访问 Development Studio **网页** `/devstudio` | ✓ | ✓ | — | — | 网页明确校验 Owner/Admin，未登录不能进入 |
| 通过 Development Studio **API** 读取研发记录 | ✓ | ✓ | ✓ | ✓ | 目前 `/api/devstudio/*` 只要求已登录；与页面门槛不同（见第 8 节） |
| 通过 Development Studio **API** 登记问题、实验、运行、评价 | ✓ | ✓ | ✓ | — | 目前 `require_editor`；前端研究者入口尚未提供 |
| 对研发变更做审批 | ✓ | ✓ | — | — | 需与变更申请人分离；审批不会自动发布 |
| 查看团队成员及邀请清单 | ✓ | ✓ | — | — | 后端接口与管理页已有开发实现 |
| 邀请 Researcher / Viewer | ✓ | ✓ | — | — | 邮件邀请，验证后设置密码 |
| 邀请或授予 Admin | ✓ | — | — | — | 只有 Owner 可操作 |
| 授予、转移、撤销 Owner | 不可通过日常界面 | — | — | — | 目前仅首次邮箱认领；Owner 转移/恢复尚未实现 |
| 管理其他 Admin 的角色与状态 | ✓ | — | — | — | 当前代码只允许 Owner 修改其他 Admin |
| 管理普通成员启用/停用、角色 | ✓ | ✓ | — | — | 服务端记录审计；不能通过普通编辑授予 Owner |
| 查看成员/研发审计记录 | ✓ | ✓ | — | — | 受管理员授权保护 |
| 合并 GitHub PR、生产部署、读数据库密钥 | 另行授权 | 另行授权 | 另行授权 | 另行授权 | **不由平台角色决定** |

说明：以上“✓”针对对应权限在 **PR #65 的开发代码**中的实现，**不是生产运行承诺**。功能使用时，还需该代码所在环境已经部署、团队认证开启，并通过邮件/浏览器验收。

## 2. Owner 首次开通（一次性）

**操作人**：有权限配置测试/生产后端的部署负责人 + 被指定的 Owner 邮箱持有人。

1. 部署负责人在**对应后端**安全设置 `TEAM_OWNER_EMAIL`、`TEAM_OWNER_SETUP_ENABLED=true`、`TEAM_AUTH_ENABLED=true`，并设置邮箱投递及 `PUBLIC_APP_URL`。绝不可把邮件服务密钥/服务器令牌放进仓库。
2. Owner 打开**该环境**的 `/account/setup`，填写被预设的邮箱，点击发送验证邮件。
3. 系统向匹配的邮箱发送**30 分钟有效的一次性链接**。其他邮箱不能获取 Owner 身份。
4. Owner 从本人邮箱打开链接，通过 `/account/setup` **自行设置 12–256 字符密码**。系统仅保存 Argon2 密码哈希，验证链接的 Token 仅以 SHA-256 摘要存储，已使用/过期链接不能再次认领。
5. Owner 返回 `/devstudio`，用邮箱和本人设置的密码登录，进入 `/account/team` 检查 Owner 身份。
6. 完成后部署负责人关闭 `TEAM_OWNER_SETUP_ENABLED` 并撤销历史初始化临时凭据；保留审计记录。

**当前指定的初始 Owner 邮箱**：见 `docs/OWNER_AND_INVITATIONS_V01.md` 中的部署参数。该邮箱目前仅在规划/开发代码中指定，**尚未激活、尚未收到真实验证邮件**。

**严禁**：仅凭用户在聊天中给出邮箱就把记录直接改为 Owner；把临时测试管理员当作正式 Owner；在聊天、Issue、GitHub 文档、截图中泄露初始密码或邮件验证链接。

## 3. Admin / Researcher / Viewer 邀请开通（常规操作）

**操作人**：Owner 或已获授权 Admin（邀请 Admin 时仅 Owner）。

1. 管理员登录 `/devstudio`，选择「团队与邀请管理」进入 `/account/team`。
2. 填写受邀邮箱、姓名和角色。普通 Admin 只能选择 Researcher/Viewer；Owner 可以额外选择 Admin。
3. 系统发送 **7 天有效、只能使用一次**的邮件邀请链接。发送失败会报错，**不会假称已发送或直接启用账户**。
4. 受邀者在邮箱里打开链接，自行设置密码，成功后按邀请角色进入 Research Atlas。
5. 管理员在邀请清单查看 `pending / used / expired / revoked`，并核对团队成员账户。尚未领取的邀请可以撤销。
6. 邀请过期或被撤销后，原链接失效；需要管理员重新发起邀请。

### 3.1 邀请处理规则

| 情形 | 正确处理 |
|---|---|
| 发错邮箱 / 成员拒绝加入 | 管理员撤销尚未使用的邀请 |
| 邮件迟迟收不到 | 检查邮件服务、垃圾箱、收件地址和频控；修复后重新发送 |
| 链接过期 | 重新发起邀请，**不可延长旧 Token** |
| 邮箱已注册 | 不再使用邀请重复创建；按身份核验后的改权/重置流程 |
| 成员要升为 Admin | Owner 在管理页审查并调整；非 Owner 不得授权 |
| 成员要求成为 Owner | 当前不提供日常转移功能，走独立审批和未来专用恢复流程 |
| 误将 Viewer 邀请为 Researcher | 可撤销未领取的邀请；已领取则由管理员按权限修改角色并保留审计 |

## 4. 四类角色的日常使用路径

### 4.1 Owner

1. 登录 `/devstudio` → `/account/team`，检查成员状态、待处理邀请、权限变更。
2. 管理团队画像及科研配置；在 Development Studio 查看实验、文档、期刊来源变更与审批。
3. 重大研发变更需保留申请人和独立审批人。**审批通过不代表 GitHub 自动合并或生产发布。**
4. 管理密钥、部署和 GitHub 权限仍通过相应平台账户完成，不在网站里共享这些凭据。

### 4.2 Admin

1. 管理日常团队账户和科研任务；邀请 Researcher/Viewer。
2. 在 Development Studio 登记及复核研发项目，审批非本人发起的变更。
3. 不得授予 Owner，不得邀请/提升其他 Admin；不能擅自代替被邀请用户设置密码。
4. 管理团队研究画像时关注版本冲突和内容来源审核。

### 4.3 Researcher

1. 使用被邀请邮箱和自己的密码登录，进入普通科研工作台。
2. 查阅共享研究画像/论文、发起 Agent/研究任务、提交研究反馈。
3. 不得新增或提升管理员、修改共享画像的正式版本或审批研发变更。
4. 当前 API 允许 Researcher 创建 DevStudio 实验/问题，但 **`/devstudio` 网页不给 Researcher 访问**。该能力暂不作为面向成员的正式入口；需要另做「提交研发反馈」前端或收紧 API，参见第 8 节。

### 4.4 Viewer

1. 使用邀请账户登录可查看的团队研究内容。
2. 不得修改团队画像、启动研究任务、提交 Idea 反馈或操作成员权限。
3. DevStudio API 当前允许登录 Viewer **读取**，但管理界面并不为其开放；公开或只读研发简报需另外设计授权入口。
4. Viewer **不是公开匿名访客**：仍需邀请、登录并遵守团队数据使用规则。

## 5. 密码、会话和账户状态

- **首次设密**：通过邮箱验证链接完成，管理员无法查看成员密码。
- **忘记密码**：在 `/account/setup?mode=reset` 输入账号邮箱；已有有效账户收到 **30 分钟一次性重置链接**。不返回可用于判断邮箱是否存在的直接令牌。
- **重置后**：原有会话被撤销，成员重新登录。
- **登录会话**：当前后端会话最长 7 天，使用随机 Token 的 SHA-256 摘要索引；可注销、撤销或停用成员。
- **多次输错**：当前已有基于账号+来源的持久失败次数限制；上线前仍需部署边缘限流、入侵监测与更严格身份保护。
- **账号停用**：后台状态立即使原会话不可用；数据、实验和审计保留，不因成员离组直接删除。
- **邮箱地址变更**：当前没有自主换绑/再次验证流程，需列入独立功能需求。
- **MFA/SSO/Owner 转移与紧急恢复**：当前尚未实现，不能在团队指南中当作已支持。

## 6. 加入团队、离开团队和交接

### 6.1 加入（Join）

管理员发出邀请 → 本人邮箱验证 → 自行设置密码 → 首次登录 → 按角色查看工作台 → 确认其可用功能符合授权范围。

### 6.2 角色变更（Change）

- 提权应经 Owner/管理员明确确认；Admin 提权只能由 Owner 执行。
- 权限变更写审计日志；成员应该被告知新权限。
- 后端必须拒绝 Viewer 自提权、Researcher 修改团队角色及普通成员操作 Owner。
- **当前例外/待修复**：`set_member_status` 保护“最后一个在岗 Admin”，但在 Owner 已存在时也会阻止移除最后一个 Admin。上线前应明确「Owner 是否替代最后 Admin」的规则并做回归。

### 6.3 离组（Offboard）

Owner/Admin 核对成员身份与需要移交的研究任务 → 停用账户、撤销待领取邀请 → 确认旧会话不能访问数据 → 在审计记录中登记操作者、原因与交接项。GitHub、Vercel、Render 和其他连接器的授权要**单独撤销**；单靠 Research Atlas 停用账户不会收回第三方平台访问权。

### 6.4 Owner 离职、失联或需要转移

**V0.1 未实现 Owner 转移或紧急恢复**。禁止直接通过管理员 UI 授予第二个 Owner。应由组织指定授权人完成离线身份核验、审批、数据库备份和审计后，按未来专用迁移流程办理。正式上线前建议把此流程设计为 P0/P1 发布门槛。

## 7. 研发治理与协作权限不是一回事

- **研发实验登记**：记录目标、基线、数据快照、运行引用、评价证据。创建记录不代表实验成功。
- **来源/期刊申请**：科研人员可以在独立反馈渠道提交建议；真正修改来源配置须经过 DevStudio 变更与复核，不在用户端直接改生产数据。
- **独立审批**：目前 DevStudio 的管理员级审批需与申请人不同；审批后仍处于待发布状态，需要 GitHub/部署环节另行核验。
- **科研发现/选题产出**：LLM、模型结果和自动任务的状态与团队成员的权限、人工科研评审要分开管理。
- **私人聊天 vs 团队共同聊天**：属于产品层数据可见性与共享规则。此前规划的“群聊只在 @GPT 或用户明确请求时调用模型”，尚需对应对话服务独立验收；当前账号角色表不能单独证明私人对话隔离或多用户群聊已经实现。

## 9. 操作和验收清单（发布门禁）

**发布前**：确认 PR #65 的后端/前端 CI、隔离测试数据库、邮件服务、对外链接域名、测试 Owner 邮箱、生产备份及回滚方案；绝不直接在正式数据库导入测试账号。

**身份验收**：未登录无法访问团队数据；错误邮箱无法认领 Owner；正确邮箱成功收到一次性链接；Token 重放/过期被拒绝；密码由用户本人设置，后端不回传明文。

**权限验收**：Owner 可邀请 Admin；Admin 可邀请普通成员但不能授予 Admin/Owner；Researcher/Viewer 无法访问受限管理页；停用后原会话不可用；密码重置撤销旧会话；所有变更留审计。

**产品验收**：管理员能够在网页发邀请、查看状态、撤销邀请；受邀者能在网页设置密码并登录；浏览器刷新后会话及授权正确；DevStudio 的 API/UI 角色矩阵一致后再面向全员推广。

**生产验收**：GitHub CI 成功 ≠ Vercel 预览构建成功 ≠ Render 后端已部署 ≠ 数据库迁移成功 ≠ 真实邮件送达 ≠ 生产发布。每项需要独立证据。
